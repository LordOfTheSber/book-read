# Установка Library Tracker

Руководство по развёртыванию приложения: что именно поднимается, чем разные способы установки
отличаются друг от друга, что задать перед запуском и как проверить, что установка живая.

Разработческий цикл (сборка, тесты, миграции) описан в [README](README.md) — здесь только установка.

---

## 1. Что разворачивается

Три контейнера за одним входом:

```
                 :80  ──301──►  :9443
браузер ──────►  nginx (frontend)  ──/api/──►  backend :8080  ──►  PostgreSQL :5432
                 отдаёт собранный SPA          Spring Boot         база и файлы БД
```

| Компонент | Образ | Что делает | Состояние |
|---|---|---|---|
| `frontend` | собирается из `frontend/Dockerfile` | nginx: отдаёт собранный React-SPA, терминирует TLS, проксирует `/api/` на бэкенд | без состояния |
| `backend` | собирается из `backend/Dockerfile` | Spring Boot: API, JWT + серверные сессии, миграции Flyway при старте | обложки на диске (`/app/storage`) |
| `db` | `postgres:16` | данные приложения | том с данными |

**Порт HTTPS — 9443, а не 443.** Так задано в `frontend/nginx/default.conf.template`, и на этот же
порт уходит редирект с 80-го. Рабочий адрес после установки — `https://<хост>:9443`; порт 80 нужен
только чтобы увести пользователя на HTTPS.

Наружу смотрит только фронтенд. Бэкенд и база доступны лишь внутри сети установки: порты 8080 и 5432
не публикуются.

## 2. Какой способ выбрать

| Способ | Когда | Раздел |
|---|---|---|
| Один сервер, Docker | боевая и тестовая установка на одну машину | [§4](#4-один-сервер-ubuntu-2204-docker) |
| Kubernetes | есть кластер и нужен отказоустойчивый фронт | [§5](#5-kubernetes) |
| Локальная разработка | писать код, гонять тесты | [§6](#6-локальная-разработка) |

## 3. Перед установкой

Общее для всех способов:

- **Секретов в репозитории нет.** Пароль базы и ключ подписи JWT не имеют значений по умолчанию —
  установщик берёт их из окружения, иначе переиспользует значения прошлой установки, иначе генерирует
  новые. Ничего заранее готовить не нужно, но и «дефолтного пароля» не существует.
- **Смена `SECURITY_JWT_SECRET` разлогинивает всех.** Токены, подписанные старым ключом, становятся
  недействительными.
- **Пароль PostgreSQL фиксируется при первичной инициализации тома.** Если том с данными жив,
  а место хранения пароля (`deploy/.env` или Secret в кластере) потеряно — новый сгенерированный
  пароль базе не подойдёт, и бэкенд не подключится. В этом случае задайте исходный пароль явно
  через `POSTGRES_PASSWORD`.
- **Домен нужен настоящий, если хотите доверенный сертификат и PWA.** Service worker регистрируется
  только в защищённом контексте, и на самоподписанном сертификате браузер откажет: приложение
  будет работать, установка на телефон и офлайн-режим — нет.

## 4. Один сервер (Ubuntu 22.04, Docker)

### 4.1. Требования

- Ubuntu 22.04, root или `sudo`.
- Доступ в интернет: скрипт ставит Docker из репозитория Docker, тянет базовые образы, собирает
  фронтенд через npm и бэкенд через Maven.
- Свободные порты 80 и 9443.
- ~4 ГБ свободного места на диск (образы сборки Maven и Node весят заметно больше итоговых).

Docker ставить заранее не нужно — установщик поставит его сам.

### 4.2. Установка

```bash
git clone <адрес репозитория> book-read
cd book-read
sudo DOMAIN=book.example.com bash deploy/install_on_ubuntu_22.sh
```

Скрипт можно запускать из любого каталога — корень репозитория он вычисляет от собственного пути.

`DOMAIN` — имя или IP, по которому пользователи будут открывать приложение. Оно попадает в
сертификат; на редирект с 80-го порта оно не влияет — туда подставляется адрес из запроса.

### 4.3. Что делает скрипт

1. Ставит базовые пакеты и Docker Engine с плагинами `buildx` и `compose`.
2. Синхронизирует репозиторий в `APP_ROOT` (если он отличается от каталога с исходниками),
   сохраняя `deploy/.env` прошлой установки.
3. Готовит сертификат в `deploy/certs`: Let's Encrypt, уже лежащий там, или самоподписанный.
4. Собирает `deploy/.env`: пароль базы и JWT-секрет — из окружения, из прошлого `deploy/.env`
   или сгенерированные. Файл создаётся с правами `0600`.
5. Открывает 80 и 9443 в `ufw`, если он установлен.
6. Собирает образы и поднимает стек `deploy/docker-compose.prod.yml`.

Скрипт идемпотентен: повторный запуск пересобирает образы и перезапускает контейнеры, не трогая
данные, пароли и сертификат.

### 4.4. Переменные

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DOMAIN` | `166.1.22.108` | Имя в сертификате и в `server_name` nginx |
| `APP_SRC` | корень репозитория | Откуда брать исходники |
| `APP_ROOT` | значение `APP_SRC` | Куда установить. Отличается от `APP_SRC` → выполняется `rsync` |
| `VITE_API_URL` | `/api/v1` | База API в сборке фронтенда |
| `POSTGRES_DB`, `POSTGRES_USER` | `library` | База и пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | **нет** | Пароль базы: из `deploy/.env` или генерируется |
| `SPRING_DATASOURCE_URL` | `jdbc:postgresql://db:5432/library` | Подключение бэкенда |
| `SPRING_DATASOURCE_USERNAME` | `library` | Пользователь бэкенда |
| `SPRING_DATASOURCE_PASSWORD` | значение `POSTGRES_PASSWORD` | Бэкенд ходит в ту же базу |
| `SPRING_PROFILES_ACTIVE` | `prod` | Профиль Spring |
| `SECURITY_JWT_SECRET` | **нет** | Ключ подписи JWT: из `deploy/.env` или генерируется |
| `SECURITY_COOKIE_SECURE` | `true` | Флаг `Secure` у кук аутентификации |
| `CERT_DIR` | `${APP_ROOT}/deploy/certs` | Где лежит сертификат, монтируемый в nginx |
| `USE_LETSENCRYPT` | `false` | Выпускать сертификат Let's Encrypt |
| `LETSENCRYPT_EMAIL` | — | Обязателен вместе с `USE_LETSENCRYPT=true` |

### 4.5. TLS

**Самоподписанный сертификат (по умолчанию).** Годится для теста: браузер покажет предупреждение,
service worker не зарегистрируется. Сертификат в `deploy/certs` переиспользуется между запусками —
чтобы выпустить новый (например, после смены `DOMAIN`), удалите оттуда `fullchain.pem` и `privkey.pem`.

**Let's Encrypt.**

```bash
sudo DOMAIN=book.example.com \
     USE_LETSENCRYPT=true LETSENCRYPT_EMAIL=admin@example.com \
     bash deploy/install_on_ubuntu_22.sh
```

Условия: `DOMAIN` — доменное имя (на IP сертификат не выпускается, скрипт остановится с ошибкой),
имя резолвится на этот сервер, порт 80 доступен снаружи. Перед выпуском установщик гасит контейнер
фронтенда, потому что `certbot --standalone` сам занимает 80-й порт.

Продление автоматическим не является: сертификат копируется в `deploy/certs` в момент установки.
Настройте `certbot renew` с последующим копированием файлов и перезапуском фронтенда либо
переустанавливайте раз в квартал.

**Свой сертификат.** Положите `fullchain.pem` и `privkey.pem` в `deploy/certs` до запуска
установщика — он их не тронет.

### 4.6. Проверка

```bash
cd <APP_ROOT>
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env ps

# SPA отдаётся
curl -k -o /dev/null -w '%{http_code}\n' https://localhost:9443/          # 200
# запрос доходит до бэкенда через прокси
curl -k https://localhost:9443/api/v1/monitoring/ping                    # ok
# защищённый метод отвечает 401 — это ответ приложения, а не сбой прокси
curl -k -o /dev/null -w '%{http_code}\n' https://localhost:9443/api/v1/items   # 401
# редирект с 80-го ведёт на тот же хост и порт 9443
curl -s -o /dev/null -w '%{redirect_url}\n' http://localhost/
```

Логи:

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs -f backend
```

Готовность бэкенда видна по строке Flyway о применённых миграциях и старту Tomcat на 8080.

### 4.7. Первый вход

Пользователей в свежей базе нет. **Первый зарегистрированный пользователь получает роль
`SUPER_ADMIN`**, все последующие — `USER`. Поэтому сразу после установки откройте
`https://<DOMAIN>:9443`, зарегистрируйтесь — и это будет учётная запись администратора.

### 4.8. Обновление

```bash
cd <APP_ROOT>
git pull
sudo bash deploy/install_on_ubuntu_22.sh
```

Пароли и JWT-секрет подхватятся из `deploy/.env`, данные и обложки останутся на своих томах,
миграции Flyway применятся при старте бэкенда.

### 4.9. Резервная копия

Резервировать нужно три вещи: базу, обложки и `deploy/.env`.

```bash
cd <APP_ROOT>
set -a; . deploy/.env; set +a

# база
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env \
  exec -T db pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" > backup.sql

# обложки
docker run --rm -v deploy_backend_storage:/data -v "$PWD":/out alpine \
  tar czf /out/covers.tar.gz -C /data .

# секреты
cp deploy/.env env-backup
```

Восстановление базы — в поднятый и пустой стек:

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env \
  exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" < backup.sql
```

`SUPER_ADMIN` может выгрузить всю базу и через приложение — раздел «Свои данные» и
`/api/v1/exports/**`.

### 4.10. Остановка и удаление

```bash
cd <APP_ROOT>
# остановить, данные сохранить
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env down
# удалить вместе с базой и обложками — необратимо
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env down -v
```

## 5. Kubernetes

### 5.1. Требования

- Настроенный `kubectl` с доступом в кластер (`kubectl` скрипт не устанавливает — поставьте
  `snap install kubectl --classic` или по инструкции Kubernetes).
- `docker` для сборки образов, `python3` и `openssl` — их скрипт поставит через apt при нехватке.
- В кластере должен быть StorageClass по умолчанию: под базу и обложки создаются PVC.
- Кластер должен уметь взять локально собранные образы: `kind`, `minikube` (скрипт загрузит образы
  сам) либо укажите `IMAGE_REGISTRY` — тогда образы уедут в реестр.

### 5.2. Установка

```bash
./deploy/install_k8s.sh
```

Скрипт собирает образы, загружает их в кластер или в реестр, подставляет переменные в
`deploy/k8s/manifest.yaml`, применяет манифест и ждёт готовности `db`, `backend`, `frontend`.

Контекст `kubectl` выбирается сам, если он единственный; поддерживаются k3s
(`/etc/rancher/k3s/k3s.yaml`), `kind` и `minikube`. Проверку можно отключить через
`SKIP_CLUSTER_CHECK=true`.

### 5.3. Переменные

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `NAMESPACE` | `book-read` | Пространство имён |
| `DOMAIN` | `23.26.124.71` | Имя в `server_name` nginx |
| `VITE_API_URL` | `/api/v1` | База API в сборке фронтенда |
| `POSTGRES_DB`, `POSTGRES_USER` | `library` | База и пользователь |
| `POSTGRES_PASSWORD` | **нет** | Из Secret `book-read-db` или генерируется |
| `SECURITY_JWT_SECRET` | **нет** | Из Secret `book-read-backend` или генерируется |
| `SECURITY_COOKIE_SECURE` | `true` | Флаг `Secure` у кук |
| `SPRING_PROFILES_ACTIVE` | `prod` | Профиль Spring |
| `DB_STORAGE_SIZE` | `1Gi` | Размер PVC базы |
| `COVERS_STORAGE_SIZE` | `1Gi` | Размер PVC с обложками |
| `BACKEND_REPLICAS` | `1` | См. [§5.5](#55-масштабирование-и-обложки) |
| `FRONTEND_REPLICAS` | `1` | Реплики nginx |
| `FRONTEND_SERVICE_TYPE` | `ClusterIP` | Тип Service фронтенда |
| `IMAGE_TAG` | `local` | Тег собираемых образов |
| `IMAGE_REGISTRY` | — | Реестр: задан → образы пушатся и тянутся оттуда |
| `IMAGE_PULL_POLICY` | `IfNotPresent` без реестра, иначе `Always` | Политика загрузки образов |
| `ROLLOUT_TIMEOUT` | `180s` | Ожидание готовности деплойментов |
| `SKIP_CLUSTER_CHECK` | `false` | Пропустить проверку доступности кластера |

### 5.4. Доступ снаружи

С `ClusterIP` (по умолчанию) снаружи не слушает ничего — это самый безопасный вариант по умолчанию,
но приложение нужно как-то открыть.

**Проброс порта — для проверки:**

```bash
kubectl port-forward service/frontend 9443:9443 -n book-read
# затем https://localhost:9443
```

Пробрасывать 80-й порт бессмысленно: он только редиректит на 9443.

**NodePort:**

```bash
FRONTEND_SERVICE_TYPE=NodePort ./deploy/install_k8s.sh
kubectl get service frontend -n book-read -o jsonpath='{.spec.ports[?(@.name=="https")].nodePort}'
```

Kubernetes выдаст порт из диапазона 30000–32767 — открывать в firewall нужно именно его, а не 9443.

**LoadBalancer** (`FRONTEND_SERVICE_TYPE=LoadBalancer`) — если у кластера есть провайдер балансировщика;
приложение окажется на внешнем адресе, порт 9443.

**Ingress** в комплект не входит. Если он у вас есть, направляйте его на Service `frontend`, порт
9443, с TLS на стороне Ingress.

### 5.5. Масштабирование и обложки

Обложки бэкенд хранит на диске (`storage.type=filesystem`), а PVC — `ReadWriteOnce`. Поэтому реплика
по умолчанию одна: две реплики либо не поднимутся (том занят на другом узле), либо будут видеть
разные наборы файлов. Чтобы масштабировать бэкенд, переключите хранилище на S3-совместимое:

```
STORAGE_TYPE=s3
STORAGE_S3_BUCKET, STORAGE_S3_REGION, STORAGE_S3_ENDPOINT,
STORAGE_S3_ACCESS_KEY, STORAGE_S3_SECRET_KEY
```

и добавьте эти переменные в `deploy/k8s/manifest.yaml` в деплоймент бэкенда — после этого
`BACKEND_REPLICAS` можно поднимать. Фронтенд масштабируется свободно, состояния у него нет.

### 5.6. Обновление, откат, удаление

Обновление — повторный запуск `./deploy/install_k8s.sh`. Тег образа между запусками не меняется,
поэтому в шаблон пода подставляется идентификатор собранного образа: без него `kubectl apply` не
увидел бы разницы и оставил бы поды на старой сборке.

```bash
kubectl rollout undo deployment/backend -n book-read   # откат
kubectl delete namespace book-read                     # удалить всё, включая PVC с данными
```

## 6. Локальная разработка

Полный цикл описан в [README](README.md); коротко — база в Docker, бэкенд и фронтенд на хосте.

```bash
cp .env.example .env          # заполните POSTGRES_PASSWORD и DB_PASSWORD одинаковым значением
docker compose up -d db       # PostgreSQL на 127.0.0.1:5432

cd backend && mvn spring-boot:run     # http://localhost:8080
cd frontend && npm ci && npm run dev  # http://localhost:5173
```

Требуется Java 21, Maven, Node.js 18+. Вне профиля `prod` JWT-секрет генерируется при каждом старте
(токены не переживают перезапуск), а `SECURITY_COOKIE_SECURE` по умолчанию `false` — иначе куки не
дошли бы по HTTP.

## 7. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| Браузер не открывает `http://<DOMAIN>` | 80-й порт только редиректит | Открывать `https://<DOMAIN>:9443` |
| Предупреждение о сертификате | Сертификат самоподписанный | Выпустить Let's Encrypt (§4.5) или принять риск для теста |
| Приложение не ставится как PWA, офлайн не работает | Service worker требует доверенного TLS | Нужен настоящий сертификат |
| `502 Bad Gateway` на `/api/` | Бэкенд не поднялся | `docker compose ... logs backend`: чаще всего пароль базы или упавшая миграция |
| Бэкенд в цикле перезапусков, в логе `password authentication failed` | Том базы создан с другим паролем | Передать исходный `POSTGRES_PASSWORD` явно |
| `Migration checksum mismatch` | Файл миграции изменён после применения | Восстановить файл или откатить базу из резервной копии |
| Бэкенд не стартует: требуется JWT-секрет | Профиль `prod` без `SECURITY_JWT_SECRET` | Проверить `deploy/.env` / Secret `book-read-backend` |
| Все разлогинены после установки | Сгенерирован новый JWT-секрет | Ожидаемо; чтобы не повторялось — сохранять `deploy/.env` |
| `certbot` падает: порт занят | 80-й держит nginx прошлой установки | Установщик гасит фронтенд сам; при ручном запуске остановите его |
| Поды `Pending` | Нет StorageClass по умолчанию или не хватает места под PVC | `kubectl describe pvc -n book-read` |
| Поды `ErrImagePull` в k8s | Образ собран локально, кластер тянет его из реестра | Указать `IMAGE_REGISTRY` или использовать kind/minikube |
| Обложки пропали после переустановки | Том с обложками удалён (`down -v`) | Восстановить из архива (§4.9) |
